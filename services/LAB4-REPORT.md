## Цель работы

Реализовать взаимодействие независимых бизнес-сервисов через синхронные REST API и асинхронный брокер RabbitMQ, обеспечить единый вход через API Gateway, устойчивость повторяемых операций и сквозной сценарий с компенсацией при сбое.

## Архитектура

Система включает четыре бизнес-сервиса: `well-registry`, `telemetry`, `ml-diagnostics` и `alert`. Каждый сервис использует собственное хранилище SQLite, размещённое в отдельном Docker volume. Nginx API Gateway принимает внешние запросы на порту 8090 и маршрутизирует их к сервисам. RabbitMQ обеспечивает обмен событиями. `notification-mock` имитирует внешний сервис доставки уведомлений и не входит в число четырёх основных бизнес-сервисов.

## Синхронные взаимодействия

1. Telemetry проверяет существование скважины запросом к внутреннему REST endpoint Registry.
2. ML Diagnostics получает данные измерения из Telemetry по REST.
3. В сценарии Saga Telemetry сохраняет измерение, затем синхронно вызывает ML Diagnostics для выполнения диагностики.
4. Alert отправляет сформированное уведомление в Notification Mock по HTTP.

## Асинхронные взаимодействия

1. После приёма измерения Telemetry публикует событие `telemetry.received`.
2. ML Diagnostics подписан на `telemetry.received`, выполняет расчёт и публикует `diagnostics.completed`.
3. Alert подписан на `diagnostics.completed`; при обнаружении аномалии сохраняет алерт и отправляет уведомление в Notification Mock.
4. Оркестратор Saga публикует `workflow.completed` при успехе или `workflow.compensated` при сбое.

Для обмена используется topic exchange `well_monitor.events`; сообщения публикуются с persistent delivery mode.

## API Gateway

Клиентские запросы выполняются через `http://localhost:8090`. Gateway маршрутизирует `/api/v1/wells`, `/api/v1/localities` и `/api/v1/promysels` в Registry; `/api/v1/telemetry` и `/api/v1/workflows` — в Telemetry; `/api/v1/predict` — в ML Diagnostics; `/api/v1/alerts` — в Alert. Health endpoints доступны по `/health/registry`, `/health/telemetry`, `/health/ml` и `/health/alert`.

## Идемпотентность и обработка ошибок

Для повторяемых операций используется заголовок `Idempotency-Key`. Registry сохраняет ключ, хэш тела запроса и сформированный ответ; повтор с тем же ключом и телом возвращает прежний результат, а повтор с другим телом завершается HTTP 409. Telemetry сохраняет ключ и SHA-256 хэш тела измерения; при совпадении ключа и тела возвращает ранее созданную запись, а при несовпадении — HTTP 409.

Ошибки API четырёх бизнес-сервисов приводятся к формату Problem Details (RFC 7807) с медиатипом `application/problem+json` и полями `type`, `title`, `status`, `detail`, `instance`. Ошибки валидации возвращают HTTP 422; ошибки отсутствующих ресурсов — HTTP 404; конфликт повторного ключа — HTTP 409; ошибка выполнения Saga — HTTP 502. Необработанные внутренние ошибки журналируются и возвращают обобщённое описание без раскрытия внутренней трассировки клиенту.

## Сквозной сценарий Saga

Endpoint `POST /api/v1/workflows/diagnose` выполняет следующие шаги:

1. Проверяет существование скважины в Registry.
2. Создаёт запись измерения в Telemetry.
3. Синхронно вызывает ML Diagnostics.
4. При успешной диагностике публикует `workflow.completed` и возвращает результат.
5. При ошибке диагностики удаляет созданную запись компенсирующей операцией и публикует `workflow.compensated`.

Если компенсационное удаление не удалось, сервис фиксирует это в журнале и возвращает отдельное сообщение о неуспешной компенсации. Публикация события компенсации также логируется отдельно.

## Автоматические тесты

Для четырёх сервисов добавлены отдельные наборы pytest-тестов. Они проверяют формирование Problem Details для ошибочных запросов; для Registry и Telemetry дополнительно проверяются повторный запрос с тем же ключом и конфликт при изменении тела запроса. Наборы запускаются последовательно скриптом `services/run-lab4-tests.ps1`, который устанавливает зависимости из `requirements-dev.txt`. Дополнительно создан интеграционный тест `services/integration-tests/test_gateway_flow.py`: он проверяет прохождение запросов через Gateway, взаимодействие Registry, Telemetry и ML, идемпотентность телеметрии и успешное завершение Saga. Для него работающий Compose-стенд должен быть запущен; зависимости устанавливаются из `services/integration-tests/requirements.txt`.

## Запуск и демонстрация

```powershell
docker compose -f docker-compose.lab4.yml up -d --build
docker compose -f docker-compose.lab4.yml ps
```

Gateway: `http://localhost:8090`. Postman-коллекция: `postman/Well-Monitor-Lab4.postman_collection.json`. Подробные сценарии, включая успешную Saga и остановку ML-сервиса для проверки компенсации, описаны в `docs/demo-scenarios.md`.

Остановка без удаления данных:

```powershell
docker compose -f docker-compose.lab4.yml down
```

## Ограничения учебной реализации

ML-диагностика использует прозрачную пороговую эвристику по давлению, температуре, расходу и вибрации; это не обученная модель Isolation Forest. `notification-mock` имитирует приём уведомлений, а не реальную доставку. Для промышленной эксплуатации потребуются дополнительные механизмы гарантированной повторной доставки уведомлений, мониторинг брокера, аутентификация межсервисных запросов и более строгая обработка конкурентных повторов.

Перед сдачей необходимо вписать ФИО и номер группы, выполнить тестовый скрипт и приложить собственные скриншоты Postman и логов успешного и компенсированного сценариев.
