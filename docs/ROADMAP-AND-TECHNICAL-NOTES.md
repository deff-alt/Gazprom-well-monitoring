# Well Monitor — развитие проекта и технические замечания

## Что добавлено в текущей итерации

- Обновлена оболочка приложения: боковая навигация, верхняя панель предприятия, компактные KPI, адаптивная сетка и единый стиль таблиц/форм. Страница `/login`, фирменная палитра и логотип Газпрома сохранены.
- Добавлен журнал `/alerts`: фильтры по критичности и статусу, назначение текущего пользователя ответственным при переводе события в работу, закрытие события.
- Добавлен модуль `/diagnostics`: статус модели, обучение Isolation Forest (только администратор), ручной инференс по последней точке скважины и автоматическое создание алерта при обнаружении аномалии.
- Дашборд показывает реальные последние алерты и считает активные события из БД.
- Внешняя выдача телеметрии проверяет принадлежность скважины промыслу начальника промысла.
- Приём телеметрии от шлюза защищён заголовком `X-Telemetry-Key`. Для демонстрации используется dev-ключ; перед развёртыванием его обязательно заменить через переменную `TELEMETRY_API_KEY`.
- Убраны всплывающие подсказки наведения с основных графиков, анимация отключена для более спокойного промышленного интерфейса.

## Запуск

```bash
docker compose up -d --build
```

- Frontend: http://localhost:5173
- API: http://localhost:8000
- Swagger: http://localhost:8000/docs

После появления не менее 20 точек телеметрии администратор может открыть «ML-диагностика» и обучить модель. Для проверки конкретной скважины нужно выбрать её и запустить диагностику. Обнаруженная аномалия попадёт в журнал алертов.

Приём одной точки телеметрии:

```http
POST /internal/v1/telemetry
Content-Type: application/json
X-Telemetry-Key: <TELEMETRY_API_KEY>
```

## Важные ограничения текущей ML-реализации

Isolation Forest — алгоритм обнаружения аномалий, а не модель прогноза времени до аварии. Число `anomaly_score` — нормированный демонстрационный индикатор отклонения, **не вероятность отказа**. Фраза «авария через 18 часов с вероятностью 73%» не должна использоваться в интерфейсе или пояснительной записке, пока нет отдельной прогнозной модели, исторических меток отказов и калибровки вероятностей.

Текущая модель обучается на накопленной телеметрии с `contamination=0.04`. Для корректного промышленного результата нужно выделить подтверждённые нормальные интервалы, исключить ремонты и уже известные аварийные периоды, нормализовать режимы работы скважин и проверить качество на независимой выборке. В реальном контуре обучение желательно версионировать, сохранять метрики и возможность отката модели.

## Что ещё стоит добавить в итоговый дипломный продукт

### Приоритет 1 — делает сервис цельным

1. **Пороговые значения по параметрам.** Отдельный справочник: параметр, нижняя/верхняя граница, единица измерения, область действия (скважина/промысел), дата действия и автор изменения.
2. **Защита от повторных алертов.** Объединение непрерывных аномальных точек в один инцидент, гистерезис, пауза повторного уведомления и журнал изменения статуса.
3. **Карточка инцидента.** История телеметрии до/после события, затронутые параметры, ответственный, комментарии, причина, предпринятые действия и результат.
4. **Качество и актуальность телеметрии.** Время последнего пакета по скважине, пропуски, дубли, невозможные значения, статус связи с датчиком.
5. **Фильтры фонда.** По промыслу, месторождению, типу скважины, статусу, уровню риска и наличию свежих данных.

### Приоритет 2 — сильная демонстрация на защите

1. **Имитация потока в реальном времени.** Отдельный скрипт-генератор, который отправляет телеметрию с заданным интервалом и позволяет включать сценарии «обводнение», «гидраты», «рост вибрации».
2. **Сравнение нормы и аномального режима.** На графике — обычный диапазон, фактическая линия и маркер времени обнаружения.
3. **Уведомления.** Внутренний центр уведомлений и, как дополнительная опция, email/Telegram через отдельный адаптер.
4. **Экспорт отчёта.** PDF/Excel по скважине, инцидентам, динамике добычи и работе диагностической модели.
5. **Панель руководителя.** Доступность фонда, доля скважин с актуальной телеметрией, инциденты по промыслам, время реакции и длительность устранения.

### Приоритет 3 — промышленное развитие

- Перевести высокочастотную телеметрию на TimescaleDB (сейчас в compose развёрнут обычный PostgreSQL 16; TimescaleDB в текущей конфигурации не включён).
- Добавить фоновые задачи для планового инференса и переобучения; не запускать ML вручную из пользовательского запроса в промышленном режиме.
- Добавить аудит действий пользователей, ротацию refresh-токенов, хранение токенов в защищённых HttpOnly-cookie и централизованный секрет-менеджмент.
- Добавить тесты RBAC для каждой роли и интеграционные тесты жизненного цикла алерта.
- Для прогноза «время до отказа» собрать размеченную историю отказов и ремонтов, определить целевое событие и горизонт прогноза, сравнить модели (например, градиентный бустинг и LSTM) и оценить precision/recall, PR-AUC, lead time и калибровку.

## Формулировка для защиты

Текущая версия реализует мониторинг фонда, приём и хранение телеметрии, ролевое разграничение доступа, выявление статистически нетипичных режимов методом Isolation Forest и управление диагностическими событиями. Это прототип аналитического слоя над SCADA/АСУ ТП, а не замена самой SCADA и не сертифицированная система противоаварийной защиты.
