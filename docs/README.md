Лабораторная работа №3. Декомпозиция и проектирование микросервисной системы
Связь с ВКР
Работа выполняется в рамках ВКР «Веб-сервис мониторинга и предиктивной диагностики скважин на основе машинного обучения» для предприятий нефтегазовой отрасли (пилотное предприятие — ООО «Газпром добыча Краснодар»).

В ВКР реализован монолитный прототип (FastAPI + PostgreSQL + React) — он нужен для проверки гипотезы: «Isolation Forest может обнаруживать аномалии в телеметрии скважин до наступления аварийных ситуаций». Монолит позволил быстро итерировать и проверять ML-модели.

Цель данной лабораторной — спроектировать микросервисную архитектуру для того же домена с учётом требований промышленной эксплуатации:

масштабирование по промыслам и месторождениям;

независимое развёртывание ML-части (переобучение модели без остановки учётной системы);

потоковая обработка высокочастотной телеметрии (до 1500 скважин × 288 показаний/сутки).

1. Анализ предметной области
1.1 Описание системы
Веб-сервис предназначен для мониторинга технического состояния фонда скважин и предиктивной диагностики осложнений (обводнение, гидратообразование, износ насосного оборудования) на нефтегазодобывающих предприятиях. Система собирает телеметрию с датчиков (давление, температура, дебиты, вибрация), анализирует её с помощью моделей машинного обучения и формирует алерты для инженерно-технического персонала.

1.2 Акторы
Актор	Роль
Оператор	Дежурный по промыслу. Просматривает текущее состояние скважин и алертов
Инженер-технолог	Ведёт учётную документацию, настраивает пороги, работает с алертами
Начальник промысла	Контролирует производство своего промысла, видит сводку и алерты
Администратор	Управляет пользователями, ролями, справочниками, ML-моделями
Внешние системы:

SCADA / АСУ ТП — источник телеметрии с датчиков (OPC UA, Modbus).

SMTP-сервер / Telegram Bot API — канал уведомлений.

Keycloak — IdP с OAuth 2.0 / OIDC.

1.3 Ключевые пользовательские сценарии
Как оператор, я хочу видеть список активных алертов своего промысла, чтобы оперативно реагировать на осложнения.

Как инженер-технолог, я хочу настроить порог аномальности для конкретной скважины, чтобы снизить ложные срабатывания.

Как инженер-технолог, я хочу видеть график телеметрии за сутки, чтобы проанализировать динамику перед аварией.

Как начальник промысла, я хочу видеть KPI по своему промыслу (добыча, число активных алертов), чтобы оценить состояние фонда.

Как администратор, я хочу запустить переобучение ML-модели, чтобы адаптировать её к новым данным.

1.4 Доменные события (упрощённый Event Storming)
СкважинаСоздана — в системе зарегистрирована новая скважина.

ТелеметрияЗаписана — от датчика получен очередной набор показаний.

АномалияОбнаружена — ML-модель выявила отклонение от нормы.

АлертСоздан — на основе аномалии сформирован алерт для инженера.

АлертВзятВРаботу — инженер назначил себя ответственным.

АлертЗакрыт — проблема устранена.

ЗамерДебитаДобавлен — оператор внёс суточный замер.

КапремонтЗапланирован — инженер запланировал ремонт.

1.5 Ограниченные контексты и глоссарии
Контекст «Реестр скважин» (well-registry)
Отвечает за учёт скважин, месторождений, промыслов. Термины:

Термин	Значение в контексте
Скважина	Инженерное сооружение с паспортными данными (номер, глубина, давление пластовое, дата ввода)
Месторождение	Геологический объект (поле, залежь) с набором скважин
Промысел	Организационная единица, обслуживающая скважины (цех, участок)
Контекст «Телеметрия» (telemetry)
Отвечает за приём и хранение показаний с датчиков. Термины:

Термин	Значение в контексте
Замер телеметрии	Запись с временной меткой и набором физических параметров (давления до/после штуцера, температура, вибрация)
Окно агрегации	Временной интервал для усреднения (1 час, 24 часа)
Контекст «ML-диагностика» (ml-diagnostics)
Отвечает за применение моделей машинного обучения. Термины:

Термин	Значение в контексте
Модель	Обученный алгоритм (Isolation Forest, LSTM Autoencoder) с версией и метриками
Anomaly score	Оценка аномальности от 0 до 1
Окно анализа	Набор точек телеметрии, подаваемых в модель
Контекст «Алерты» (alert)
Отвечает за жизненный цикл алертов. Термины:

Термин	Значение в контексте
Алерт	Событие, требующее реакции инженера (проблема на скважине)
Приоритет	info / warning / critical
Статус	new / in_progress / resolved / dismissed
Контекст «Производство» (production)
Отвечает за замеры дебита, экспертизы, ремонты. Термины:

Термин	Значение в контексте
Замер дебита	Суточный объём добычи (газ, жидкость)
Экспертиза	Периодическая проверка оборудования (КГ, ФА)
Капремонт	Плановый или аварийный ремонт скважины
Контекст «Уведомления» (notification)
Отвечает за доставку сообщений. Термины:

Термин	Значение в контексте
Канал	email / telegram / sms
Запись доставки	Лог отправки с результатом
2. Список и описание сервисов
2.1 Карточки сервисов
well-registry-service
Поле	Значение
Название	well-registry-service
Ответственность	Учёт скважин, месторождений, промыслов. CRUD и паспортизация
Владеет данными	wells, localities, promysels
Предоставляет	REST API /api/v1/wells, /api/v1/localities, /api/v1/promysels, /internal/v1/wells/{id}. Публикует well.created, well.updated
Зависит от	Keycloak (JWT для авторизации)
Нефункциональные требования	Низкая нагрузка (1000–2000 скважин), критичность высокая (паспортные данные), допустимая задержка < 200 мс
Обоснование границы	Разные нефункциональные требования с телеметрией: паспортные данные читаются редко, телеметрия — поток. Разделение позволяет масштабировать их независимо
telemetry-service
Поле	Значение
Название	telemetry-service
Ответственность	Приём, хранение, агрегация телеметрии с датчиков
Владеет данными	telemetry (TimescaleDB)
Предоставляет	POST /internal/v1/telemetry (приём от шлюза), GET /api/v1/telemetry/{wellId} (графики для UI). Публикует telemetry.recorded
Зависит от	well-registry-service (валидация well_id через sync-вызов или копию данных через события)
Нефункциональные требования	Высокая нагрузка (~430 000 точек/сутки), критичность средняя (не блокирует учёт), допустимая задержка < 50 мс
Обоснование границы	Высокочастотный поток с совсем другими требованиями к хранению (TimescaleDB, retention policy 90 дней)
ml-diagnostics-service
Поле	Значение
Ответственность	Обучение и применение ML-моделей, оценка аномалий
Владеет данными	ml_models, model_versions (S3/MinIO для артефактов)
Предоставляет	POST /api/v1/predict, POST /api/v1/models/train (admin). Подписан на telemetry.recorded. Публикует anomaly.detected, anomaly.check_failed
Зависит от	telemetry-service (sync-запрос окна данных)
Нефункциональные требования	Вычислительно тяжёлый, критичность средняя, допустимая задержка инференса < 5 с
Обоснование границы	Независимый цикл релизов (переобучение), свой стек (Python + PyTorch/scikit-learn), свои ресурсы (CPU/GPU)
alert-service
Поле	Значение
Ответственность	Жизненный цикл алертов: создание, назначение, закрытие
Владеет данными	alerts
Предоставляет	GET /api/v1/alerts, PATCH /api/v1/alerts/{id}. Подписан на anomaly.detected. Публикует alert.created, alert.resolved
Зависит от	well-registry-service (подтянуть паспорт для отображения)
Нефункциональные требования	Средняя нагрузка (десятки алертов в сутки), критичность высокая (реакция на аварию)
Обоснование границы	Отдельная модель «Алерт» (для ML это просто anomaly, для инженера — задача с SLA и статусом)
production-service
Поле	Значение
Ответственность	Замеры дебита, экспертизы КГ/ФА, капремонты
Владеет данными	production_rates, kg_expertises, fa_expertises, workovers
Предоставляет	GET /api/v1/production/{wellId}, POST /api/v1/workovers
Зависит от	well-registry-service (валидация well_id)
Нефункциональные требования	Низкая нагрузка, критичность средняя
Обоснование границы	Учётная бизнес-логика, отдельная от мониторинга. Ремонты/экспертизы не участвуют в real-time сценариях
notification-service
Поле	Значение
Ответственность	Отправка email/telegram уведомлений по алертам
Владеет данными	notification_log (MongoDB)
Предоставляет	Подписан на alert.created, alert.resolved
Зависит от	SMTP-сервер / Telegram Bot API (внешние)
Нефункциональные требования	Низкая нагрузка, критичность низкая, но канал может падать
Обоснование границы	Внешний сервис может быть недоступен, это не должно блокировать алерты. Async через Kafka
2.2 Отвергнутые альтернативы декомпозиции
Объединить alert-service и notification-service — отказались: SMTP может падать, нотификации не должны блокировать создание алертов. Разные SLA.

Держать телеметрию и скважины в одной БД — отказались: разные нагрузки, разные retention policy.

Свой auth-service вместо Keycloak — отказались: Keycloak покрывает OAuth 2.0 / OIDC «из коробки», своя реализация — неоправданный риск.

Дробить production-service на workovers-service, expertises-service, rates-service — отказались: слишком мелко, одна бизнес-область «производственный учёт», меняется одновременно.

Объединить ml-diagnostics и telemetry — отказались: ML-часть требует Python/PyTorch и переобучения, телеметрия — просто приём и хранение. Разный цикл релизов.

3. Выбранное ПО с обоснованием
Компонент	Для каких сервисов	Обоснование
PostgreSQL	well-registry, alert, production	Транзакции, строгая схема, связи (FK). alerts требует UNIQUE по (well_id, source_event_id) — реляционная СУБД справляется
TimescaleDB (расширение PostgreSQL)	telemetry	Гипертаблицы для временных рядов, встроенная агрегация time_bucket(), сжатие старых данных
Redis	telemetry (кэш последних показаний), alert (кэш счётчиков для дашборда)	Быстрое чтение «последние N точек» для UI, где не нужен весь исторический ряд
Apache Kafka	telemetry → ml → alert → notification	Высокий поток (~430 000 событий/сутки), несколько независимых подписчиков, повторное чтение (ML может переиграть историю)
Nginx	точка входа клиента	Маршрутизация по path prefix, проверка JWT (subrequest к Keycloak), rate limiting
Keycloak	все сервисы (авторизация)	OAuth 2.0 / OIDC, единое хранилище пользователей и ролей, JWT со встроенными claims
MinIO (S3)	ml-diagnostics	Хранение артефактов моделей (.joblib, .pt), датасетов для обучения
MongoDB	notification	Гибкая схема для логов отправок (разные поля для email/telegram)
Что НЕ выбрали и почему:

Elasticsearch — не нужен полнотекстовый поиск, обходимся SQL-запросами.

GraphQL вместо REST — команда не знакома с ним, REST + OpenAPI проще.

Kubernetes — для учебного проекта избыточен, хватает docker-compose.

6. Сквозной сценарий с компенсирующими действиями
Сценарий: «Обнаружение аномалии и уведомление инженера»

6.1 Успешный путь
Датчик → telemetry-service. POST /internal/v1/telemetry с 6 полями (давление/температура до/после штуцера, забойное давление, вибрация). Сервис валидирует well_id (sync к well-registry) и сохраняет в TimescaleDB.

telemetry-service → Kafka. Публикует событие telemetry.recorded в топик telemetry с ключом wellId.

ml-diagnostics-service читает событие. Забирает окно за 24 часа через GET /internal/v1/telemetry/{wellId}?window=24h (sync). Прогоняет через Isolation Forest.

anomaly_score > 0.85 → публикует anomaly.detected в топик diagnostics с полезной нагрузкой: { wellId, parameter: "vibration", anomalyScore, severity: "critical", windowStart, windowEnd }.

alert-service читает событие. Проверяет уникальность по source_event_id (UNIQUE в БД) — если не дубликат, создаёт Alert со статусом NEW. Публикует alert.created.

notification-service читает alert.created. Отправляет email инженеру и сообщение в Telegram. Пишет результат в notification_log (idempotency по (alert_id, channel)).

Инженер в UI видит алерт на /alerts, берёт в работу → PATCH /api/v1/alerts/{id} → статус IN_PROGRESS, assigned_to = current_user.

6.2 Сбой на шаге 3 (ml-diagnostics упал)
Событие telemetry.recorded остаётся в Kafka (offset не закоммичен).

При подъёме ml-diagnostics вычитывает накопленные события.

Обработчик идемпотентен: хранит processed_event_ids (Redis с TTL 24ч), не пересчитывает.

Если модель падает на инференсе 3 раза подряд → событие отправляется в DLQ diagnostics.dlq. Фоновая задача публикует anomaly.check_failed → alert-service создаёт «информационный» алерт, что диагностика для этой скважины недоступна.

6.3 Сбой на шаге 5 (alert-service упал)
anomaly.detected остаётся в топике diagnostics.

При подъёме alert-service вычитывает и создаёт алерты.

Идемпотентность по source_event_id: если событие пришло повторно — UNIQUE constraint предотвращает дубликат.

6.4 Сбой на шаге 6 (notification-service упал)
alert.created остаётся в топике alerts.

При подъёме notification-service отправляет.

Idempotency: notification_log содержит UNIQUE (alert_id, channel). Если email уже отправлен — второй раз не отправляется.

6.5 Компенсация (Saga)
Для полноценной Saga с 3+ сервисами рассмотрим сценарий «Создание скважины с инициализацией связанных данных»:

Админ → well-registry. POST /api/v1/wells с Idempotency-Key. Сервис создаёт Well со статусом active (локальная транзакция).

well-registry → Kafka. Публикует well.created.

production-service читает well.created → создаёт пустую запись для будущих замеров дебита.

alert-service читает well.created → подписывает скважину на алерты (создаёт подписку).

Компенсация при сбое:

Если production-service упал на шаге 3 → событие остаётся в Kafka, обработка повторится.

Если alert-service упал → то же.

Если админ передумал и удаляет скважину → well-registry публикует well.deleted → production и alert каскадно чистят данные (компенсирующее действие).

9. Итоги
Спроектирована микросервисная архитектура для домена мониторинга и предиктивной диагностики скважин:

6 бизнес-сервисов с чёткими границами по bounded contexts.

6 синхронных взаимодействий (client → gateway → services, плюс внутренние).

5 асинхронных событий через Kafka.

Сквозной сценарий «обнаружение аномалии → уведомление» с описанием сбоев на каждом шаге и компенсаций.

У каждого сервиса своё хранилище (PostgreSQL, TimescaleDB, Redis, MongoDB, MinIO).

Авторизация через Keycloak, клиент ходит только через API Gateway.

Архитектура готова к реализации в последующих лабораторных и является прод-расширением монолитного прототипа ВКР.
